This page prepares the **cluster**: everything here is `kubectl` and plain
manifests, no Helm. The application itself is installed by the
[Helm chart](/deployment/helmchart), once the cluster passes the checks below.

Every step was run on a real cluster (k0s v1.36.3, three nodes) before being
written down. The commands are the ones that worked; the **Traps** section at
the end lists what went wrong on the way, with the symptom that gives each one
away.

## What you need before starting

| | |
| --- | --- |
| A Kubernetes cluster | 1.28 or later. Three nodes of 4 vCPU / 8 GB is comfortable for the full stack |
| `kubectl` | within one minor version of the server |
| A storage class | **the cluster does not necessarily have one** — [step 2](#2-storage) |
| An ingress controller | for a public address — [step 3](#3-ingress-controller) |
| A DNS name | pointed at the ingress load balancer |

## 1. Reach the cluster

```bash
export KUBECONFIG=~/.kube/config
kubectl get nodes
```

Every node must be `Ready`. `kubectl version` should show a client at most one
minor version away from the server; further apart, some commands fail in
puzzling ways.

## 2. Storage

**Check first — this is the single most common reason nothing starts.**

```bash
kubectl get storageclass
```

`No resources found` means no volume can ever be created: PostgreSQL and the
data volume would stay `Pending` forever, and the pods with them. Managed
clusters differ wildly here; some ship a class, some only offer object storage
(which does **not** suit PostgreSQL).

If the list is empty, `local-path-provisioner` gives you node-local volumes in
one manifest:

```bash
curl -sL -o local-path-storage.yaml \
  https://raw.githubusercontent.com/rancher/local-path-provisioner/v0.0.37/deploy/local-path-storage.yaml
kubectl apply -f local-path-storage.yaml
kubectl -n local-path-storage rollout status deploy/local-path-provisioner --timeout=120s
```

Make it the default, otherwise claims that name no class — the chart's — stay
unbound:

```bash
kubectl patch storageclass local-path \
  -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
kubectl get storageclass
```

You want to read `local-path (default)`.

<Warning>
  A node-local volume lives on **one** node's disk. It is enough for a single
  PostgreSQL replica and for `ReadWriteOnce` data, and it is not
  highly available: losing the node loses the volume. Back the database up, or
  use your provider's block CSI driver when it has one.
</Warning>

Prove it works before going further — and mind that the check needs a **pod**,
not just a claim ([Trap 1](#trap-1-a-pvc-that-stays-pending-on-purpose)):

```bash
kubectl apply -f - <<'YAML'
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: probe-pvc}
spec:
  accessModes: ["ReadWriteOnce"]
  resources: {requests: {storage: 1Gi}}
---
apiVersion: v1
kind: Pod
metadata: {name: probe-pod}
spec:
  restartPolicy: Never
  containers:
    - name: writer
      image: busybox:1.37
      command: ["sh","-c","echo ok > /data/marker && cat /data/marker && sleep 20"]
      volumeMounts: [{name: data, mountPath: /data}]
  volumes:
    - {name: data, persistentVolumeClaim: {claimName: probe-pvc}}
YAML
sleep 25 && kubectl get pvc probe-pvc && kubectl logs probe-pod
kubectl delete pvc probe-pvc pod probe-pod
```

`Bound`, and `ok` in the logs. Anything else, stop here: the rest cannot work.

## 3. Ingress controller

Needed only for a public address; skip it if you will use `port-forward`.

Install **Traefik** or **ingress-nginx** — most managed Kubernetes offerings
have both as a one-click add-on, which is the simplest path since the
provider then also wires the load balancer. Then:

```bash
kubectl get ingressclass
kubectl get svc -A | grep LoadBalancer
```

Note the class name (`traefik`, `nginx`…) and the `EXTERNAL-IP` of the
controller's service: that address is what your DNS record will point to.

## 4. cert-manager and an issuer

Installing cert-manager is not enough — **it issues nothing until an issuer
exists**.

```bash
kubectl get pods -n cert-manager
```

Then create the issuers. Two of them: production, and staging — which you use
first, because Let's Encrypt blocks an account for a week after five failures
in an hour, and the first attempt rarely succeeds.

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-staging
spec:
  acme:
    server: https://acme-staging-v02.api.letsencrypt.org/directory
    email: you@example.com          # Let's Encrypt mails expiry notices here
    privateKeySecretRef:
      name: letsencrypt-staging-account-key
    solvers:
      - http01:
          ingress:
            ingressClassName: traefik   # your class from step 3
```

The production issuer is the same with
`https://acme-v02.api.letsencrypt.org/directory` and its own key secret name.
Both are ready-made in the hosting repository under
`k8s/cert-manager/cluster-issuer-letsencrypt.yaml`.

```bash
kubectl apply -f k8s/cert-manager/cluster-issuer-letsencrypt.yaml
kubectl get clusterissuer
```

`READY: True` on both means cert-manager registered with the ACME servers.

<Warning>
  Use `ingressClassName`, **not** `class`. The latter goes through the legacy
  `kubernetes.io/ingress.class` annotation and is only recommended for
  ingress-gce. With it, the challenge Ingress is created without a recognised
  class, the controller ignores it, and the certificate sits at
  `Ready: False` while nothing reports an error.
</Warning>

## 5. HTTPS redirect (Traefik)

A certificate does not close the clear-text entrance: once the site is public,
`http://` keeps serving it unless something redirects. With Traefik, that
something is a Middleware, cluster-side, ready-made in the hosting repository:

```bash
kubectl create namespace apowerb      # the Middleware lives in the application's namespace
kubectl apply -f k8s/traefik/redirect-https.yaml
kubectl -n apowerb get middleware redirect-https
```

The application's Ingress opts into it with one annotation — see
[Going public](/deployment/helmchart#4-going-public). With ingress-nginx there
is nothing to apply: `ssl-redirect` acts as soon as the Ingress has a TLS
section.

## The manifests in `k8s/`

The hosting repository's `k8s/` folder holds what lives **beside** an
installation — cluster-wide objects an application chart should not create:

| Path | What it is |
| --- | --- |
| `k8s/cert-manager/cluster-issuer-letsencrypt.yaml` | the staging and production issuers — [step 4](#4-cert-manager-and-an-issuer) |
| `k8s/traefik/redirect-https.yaml` | the HTTP → HTTPS Middleware — [step 5](#5-https-redirect-traefik) |

`00-namespace.yaml` … `05-ingress.yaml` are older: they predate the chart and
describe an incomplete stack — no orchestrator, no log store, no collector, no
data volume, an Ingress on `apowerb.local`. `kubectl apply -f k8s/` installs
something that *looks* right and is not. Do not use them to install the
application.

## Traps

### Trap 1: a PVC that stays Pending on purpose

**Symptom.** You create a claim to test the storage; it stays `Pending`. It
looks like the storage is broken.

**Cause.** Storage classes with `volumeBindingMode: WaitForFirstConsumer` —
`local-path` among them — only create the volume when a **pod** needs it. This
is by design: the volume is placed on the node the pod is scheduled to.

**Remedy.** Test with a claim *and* a pod, as in [step 2](#2-storage).
`kubectl get storageclass` shows the mode.

### Trap 2: no storage class at all

**Symptom.** Same `Pending`, but with a pod waiting too, and
`kubectl describe pvc` says: `no persistent volumes available for this claim
and no storage class is set`.

**Cause.** The cluster has no default storage class — common on lean managed
clusters.

**Remedy.** [Step 2](#2-storage). Check `kubectl get storageclass` **before**
installing, not after wondering why nothing starts.

### Trap 3: a certificate stuck at Ready: False

**Symptom.** `kubectl get certificate` shows `READY: False` and stays there,
without an obvious error.

**Causes, in the order worth checking.**

1. The DNS name does not resolve to the ingress load balancer yet, or port 80
   is closed — the HTTP-01 challenge needs both.
2. The issuer uses `class` instead of `ingressClassName` (see
   [step 4](#4-cert-manager-and-an-issuer)).
3. The Let's Encrypt rate limit has been hit — five failures in an hour blocks
   the account for a week. This is what the staging issuer is for.

```bash
kubectl -n apowerb describe certificate apowerb-tls
kubectl -n apowerb get challenge
```

The `Challenge` object names the real reason.
